# Техническое задание API-03: авторизация, сессии и онбординг

Статус: готово к реализации после интеграции API-02.  
Рабочая ветка: `feature/auth`.  
Связанные требования: FR-API-12, FR-API-13, FR-API-20–27, FR-API-31.  
Контракты: `contracts/web.openapi.yaml`, `contracts/session.openapi.yaml`.  
Архитектурное решение: `docs/adr/0003-authentication-and-tenant-access.md`.

## 1. Цель

Реализовать полный путь от регистрации пользователя до начала работы в компании:

1. регистрация администратора или оператора без компании;
2. вход, серверная сессия, access JWT и refresh-токен;
3. чтение и изменение собственного профиля;
4. создание компании администратором;
5. получение персонального кода оператором;
6. создание, принятие и отклонение приглашения;
7. выход и отзыв сессии;
8. проверка пользовательской сессии сервисом аналитики.

Результат должен заменить auth-моки панели реальным API, не ослабляя изоляцию компаний и не доверяя роли или компании из JWT без проверки текущего состояния в БД.

## 2. Зависимости и границы

### 2.1. Обязательная зависимость

Перед реализацией ветку необходимо перебазировать или слить с результатом API-02. Auth использует следующие изменения API-02:

- администратор без компании разрешён ограничением `chk_user_company_role`;
- `audit_logs.company_id` допускает `NULL` для действий до онбординга;
- схема развивается версионированными SQL-миграциями;
- прикладные запросы выполняются под tenant-ролью и RLS;
- секреты не хранятся в открытом виде.

Auth-миграция должна быть следующей версией после API-02. Нельзя повторно реализовывать или заменять миграцию API-02 внутри `feature/auth`.

### 2.2. Входит в API-03

- публичные auth-методы и auth middleware;
- серверные пользовательские сессии;
- регистрация и собственный профиль;
- создание первой компании администратором со стартовыми SLA и расписанием;
- персональные коды и приглашения операторов;
- внутренний `GET /internal/auth/v1/session`;
- audit-записи auth и онбординга;
- обновление auth-клиента панели для refresh single-flight.

### 2.3. Не входит в API-03

- восстановление и смена пароля;
- второй фактор аутентификации;
- управление уже прикреплёнными сотрудниками, блокировка, исключение и смена L1/L2;
- настройка Telegram-бота, FAQ, редактирование SLA и расписания;
- WebSocket-аутентификация;
- ротация refresh-токена при каждом refresh;
- внешние OAuth/OIDC-провайдеры.

## 3. Роли и состояния пользователя

| Регистрационная роль | Роль в БД после регистрации | Компания | Доступ до онбординга |
|---|---|---|---|
| `admin` | `admin` | `NULL` | профиль, logout, создание компании |
| `operator` | `unassigned_operator` | `NULL` | профиль, logout, код подключения, приглашения |

После создания компании администратор сохраняет роль `admin`. После принятия приглашения оператор получает `operator_l1` или `operator_l2`, выбранную администратором.

Пользователь без компании не получает доступ к данным компаний, очередям, тикетам и аналитике. Проверка этого правила выполняется до бизнес-операции.

## 4. Публичный HTTP API

Все пути начинаются с `/api`. JSON публичного API использует `camelCase`. Ошибка имеет единую форму:

```json
{
  "error": {
    "code": "ERROR_CODE",
    "message": "Safe message",
    "details": null,
    "request_id": "5979691d-f67a-4c85-92de-203fcb4a94bc"
  }
}
```

OpenAPI должен быть обновлён до начала написания HTTP-обработчиков. Фактический обработчик и контракт не могут расходиться.

### 4.1. `POST /auth/register`

Запрос:

```json
{
  "login": "operator_1",
  "password": "strong-password",
  "fullName": "Иван Иванов",
  "role": "operator"
}
```

Правила:

- метод публичный;
- `login` нормализуется через `TrimSpace` и Unicode lowercase;
- уникальность логина регистронезависимая и обеспечивается БД;
- пароль не обрезается и не нормализуется;
- `operator` преобразуется в `unassigned_operator`;
- пользователь, серверная сессия и audit-запись создаются атомарно;
- ответ сразу аутентифицирует пользователя.

Успех: `201` и `AuthResponse`:

```json
{
  "accessToken": "...",
  "refreshToken": "...",
  "user": {}
}
```

Ошибки:

- `409 LOGIN_ALREADY_EXISTS`;
- `422 VALIDATION_ERROR`;
- `503 SERVICE_UNAVAILABLE` при недоступности хранилища сессий.

### 4.2. `POST /auth/login`

Запрос содержит `login` и `password`. Для неизвестного логина, неверного пароля, заблокированного пользователя и временно заблокированного входа возвращается один ответ:

- `401 INVALID_CREDENTIALS`.

Нельзя раскрывать существование логина, блокировку или причину отказа. Для неизвестного логина выполняется проверка заранее подготовленного dummy Argon2id-хэша, чтобы сократить различие времени ответа.

Успех: `200 AuthResponse`. Каждый успешный вход создаёт новую независимую серверную сессию и сбрасывает счётчики неудачных попыток пользователя.

### 4.3. `POST /auth/refresh`

Метод публичный и не требует действующего access JWT.

Запрос:

```json
{ "refreshToken": "..." }
```

Успех:

```json
{ "accessToken": "..." }
```

В API-03 refresh-токен не ротируется. Он действует до абсолютного истечения сессии, 24 часов бездействия или отзыва. Успешный refresh считается публичной активностью и обновляет `last_activity_at`.

Следующие случаи возвращают `401 UNAUTHORIZED`:

- токен не найден или хэш не совпал;
- сессия отозвана;
- истёк абсолютный или неактивный срок;
- пользователь заблокирован;
- пользователь удалён;
- текущая роль пользователя недопустима.

### 4.4. `POST /auth/logout`

Требует access JWT. По `sid` атомарно отзывает текущую серверную сессию. Повторный logout той же сессии безопасен и возвращает `204`.

После отзыва не должны работать ни access JWT, ни refresh-токен этой сессии. Другие сессии пользователя не отзываются.

### 4.5. `GET /auth/me`

Возвращает актуального пользователя из БД, включая текущие `companyId`, `companyName`, `role` и `isBlocked`. Значения роли и компании из JWT для ответа не используются.

Метод доступен пользователю без компании.

### 4.6. `PATCH /auth/me`

Новый метод, который необходимо добавить в `web.openapi.yaml`.

Запрос:

```json
{ "fullName": "Новое имя" }
```

В API-03 разрешено менять только `fullName`. Логин, роль, компанию, блокировку и пароль этим методом изменить нельзя. Неизвестные поля отклоняются как `422 VALIDATION_ERROR`.

Успех: `200 User`.

### 4.7. `POST /company`

Доступен только действующему пользователю с ролью `admin` и `company_id IS NULL`.

Запрос:

```json
{
  "name": "ООО Поддержка",
  "description": "Необязательное описание",
  "timezone": "Europe/Moscow"
}
```

В одной транзакции API:

1. блокирует строку администратора;
2. повторно проверяет отсутствие компании;
3. создаёт компанию;
4. связывает администратора с компанией;
5. создаёт семь строк расписания: понедельник–пятница 09:00–18:00, суббота и воскресенье — выходные;
6. создаёт активную SLA-политику версии 1: L1 `15/120/10`, L2 `5/60/5` минут;
7. создаёт audit-запись.

`bot_config` без настоящего токена не создаётся. Его создание относится к настройке бота.

Успех: `201 CompanyWithUser`. Существующий access JWT остаётся применимым: middleware всегда перечитывает компанию и роль из БД.

Ошибки:

- `403 ACCESS_DENIED` для не-администратора;
- `409 COMPANY_ALREADY_CREATED`, если администратор уже связан с компанией;
- `422 VALIDATION_ERROR` для неверного IANA timezone или полей компании.

### 4.8. `GET /operator/connection-code`

Доступен только `unassigned_operator` без компании.

- возвращает текущий неиспользованный код либо атомарно создаёт новый;
- код состоит из шести символов безопасного алфавита `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`;
- коллизия повторяет генерацию;
- срок действия — до ближайших `00:00` в `Europe/Moscow`;
- истёкший или использованный код не возвращается;
- код нельзя писать в access-логи, audit details и сообщения ошибок.

Успех: `200 ConnectionCode`.

### 4.9. `POST /operator/invitations`

Новый метод для администратора, который необходимо добавить в `web.openapi.yaml`.

Запрос:

```json
{
  "connectionCode": "K7M4QX",
  "roleToAssign": "operator_l1"
}
```

Доступен только администратору активной компании. API находит действующий код, проверяет, что оператор ещё не принадлежит компании, и создаёт pending-приглашение. Повтор для той же пары компания/оператор возвращает существующее pending-приглашение и не создаёт дубликат.

Успех: `201 Invitation` для новой записи, `200 Invitation` для идемпотентного повтора.

Ошибки:

- `400 INVALID_CONNECTION_CODE` без уточнения причины;
- `403 ACCESS_DENIED`;
- `409 OPERATOR_ALREADY_ASSIGNED`;
- `429 TOO_MANY_ATTEMPTS`.

### 4.10. `GET /operator/invitations/pending`

Доступен только `unassigned_operator`. Возвращает pending-приглашения пользователя, отсортированные по `createdAt, id`. Пустой результат — `200 []`.

Перед выдачей просроченные приглашения переводятся в `expired`, если связанный код уже истёк или использован.

### 4.11. `POST /operator/invitations/{invitationId}/accept`

В одной транзакции и с блокировкой строк пользователя, кода и приглашения:

- проверяет принадлежность приглашения текущему пользователю;
- повторно проверяет статус `pending`;
- повторно проверяет действительность кода;
- повторно проверяет `company_id IS NULL` и роль `unassigned_operator`;
- связывает пользователя с компанией и назначает L1/L2;
- помечает код использованным;
- переводит приглашение в `accepted`;
- остальные pending-приглашения пользователя переводит в `expired`;
- создаёт audit-запись.

Успех: `200 User`.

При двух одновременных accept только один может завершиться успешно. Второй возвращает `409 OPERATOR_ALREADY_ASSIGNED` или `409 INVITATION_NOT_PENDING` без частичных изменений.

### 4.12. `POST /operator/invitations/{invitationId}/reject`

Доступен только владельцу pending-приглашения. Переводит его в `rejected`, не расходует персональный код и возвращает `204`. Повтор для уже rejected записи также возвращает `204`.

Чужой UUID возвращает `404 INVITATION_NOT_FOUND`, а не раскрывает существование объекта.

## 5. Внутренний API аналитики

### `GET /internal/auth/v1/session`

Маршрут не публикуется через внешний Nginx. Требует:

- `Authorization: Bearer <access JWT>`;
- канонический UUID в `X-Request-Id`.

Отсутствующий или некорректный `X-Request-Id` возвращает `400 VALIDATION_ERROR`; этот ответ необходимо добавить в `session.openapi.yaml`.

Успех:

```json
{
  "user_id": "8cb36d3a-ac56-4ef6-aa74-b3fca6184fd4",
  "company_id": "0b1c9a3e-5d0e-4c53-9d6e-0a7f2f6c1b11",
  "role": "admin",
  "session_expires_at": "2026-11-20T10:00:00Z"
}
```

`session_expires_at` равен минимуму из `access exp`, абсолютного срока сессии и `last_activity_at + 24h`.

- недействительный JWT, отозванная/истёкшая сессия и заблокированный пользователь: `401 UNAUTHORIZED`;
- действительный пользователь без компании: `403 ACCESS_DENIED`;
- ошибка БД или проверки сессии: `503 SERVICE_UNAVAILABLE`.

Вызов внутреннего `/session` не обновляет `last_activity_at`.

## 6. Пароли и токены

### 6.1. Пароли

- длина: 8–128 Unicode-символов;
- пароль может содержать пробелы, не применяется `TrimSpace`;
- хэш: Argon2id с индивидуальной случайной солью;
- параметры первой версии: memory 64 MiB, iterations 3, parallelism 2, salt 16 bytes, key 32 bytes;
- хранится PHC-строка с версией и параметрами;
- сравнение выполняется constant-time;
- пароль, хэш и соль не журналируются и не попадают в ошибки.

### 6.2. Refresh-токен

- 32 случайных байта из CSPRNG, кодирование base64url без padding;
- в БД хранится только SHA-256 хэш;
- срок сессии — 7 суток;
- токен выдаётся только в ответе register/login;
- API-03 не ротирует refresh при использовании.

### 6.3. Access JWT

- разрешён только заранее заданный алгоритм `HS256`;
- нельзя принимать алгоритм из токена без allowlist;
- обязательные claims: `sub`, `sid`, `jti`, `iss`, `aud`, `iat`, `nbf`, `exp`;
- `sub` — UUID пользователя, `sid` — UUID серверной сессии;
- срок — максимум 24 часа и не позже абсолютного срока сессии;
- роль и компания в JWT не являются источником авторизации;
- `SECRET`, issuer и audience загружаются из конфигурации и не выводятся в лог.

## 7. Серверная сессия и middleware

Каждый защищённый запрос выполняет проверки в следующем порядке:

1. наличие Bearer-заголовка;
2. синтаксис, алгоритм, подпись и стандартные claims JWT;
3. существование `sid` и соответствие `session.user_id == sub`;
4. отсутствие `is_revoked`;
5. абсолютный срок `expires_at`;
6. срок бездействия `last_activity_at + 24h`;
7. существование и отсутствие блокировки пользователя;
8. загрузка актуальной роли и компании;
9. проверка права на конкретную операцию;
10. выполнение бизнес-операции.

Авторизация обязана завершиться до изменяющей бизнес-операции. Это позволяет панели безопасно повторить запрос ровно один раз после успешного refresh.

Только успешный публичный защищённый запрос и успешный refresh считаются активностью. Обновление `last_activity_at` можно ограничить одним SQL update в минуту. Health/readiness, WebSocket heartbeat и внутренний `/session` активностью не считаются.

## 8. Защита от перебора

### 8.1. Login

- окно: 10 минут;
- после пяти неудач вход блокируется на 15 минут;
- счётчик общий для всех экземпляров API и хранится в PostgreSQL;
- обновление счётчика выполняется под блокировкой строки пользователя;
- успешный login сбрасывает окно, счётчик и `login_locked_until`;
- внешний ответ всегда `INVALID_CREDENTIALS`.

### 8.2. Коды подключения

- не более пяти неудачных вводов кода за 10 минут на администратора;
- после превышения — `429 TOO_MANY_ATTEMPTS` на 15 минут;
- успешное создание приглашения сбрасывает счётчик;
- лимит общий для экземпляров API;
- код не отражается в тексте ошибки.

Лимиты и интервалы задаются конфигурацией, но значения по умолчанию соответствуют этому разделу. Нулевые и отрицательные значения конфигурации запрещены.

## 9. Изменения схемы данных

Auth-миграция должна быть атомарной и включать минимум:

### `users`

- `created_at timestamptz NOT NULL DEFAULT now()`;
- `updated_at timestamptz NOT NULL DEFAULT now()`;
- `failed_login_count integer NOT NULL DEFAULT 0`;
- `failed_login_window_started_at timestamptz NULL`;
- `login_locked_until timestamptz NULL`;
- регистронезависимый unique-индекс на нормализованный логин;
- проверку допустимых сочетаний `company_id` и `role` из API-02.

До создания индекса миграция должна обнаружить конфликтующие логины без учёта регистра и завершиться понятной ошибкой без автоматического переименования пользователей.

### `user_sessions`

- `created_at timestamptz NOT NULL DEFAULT now()`;
- `last_activity_at timestamptz NOT NULL`;
- `revoked_at timestamptz NULL`;
- существующие `refresh_token_hash`, `expires_at`, `is_revoked` сохраняются;
- индекс для поиска активной сессии по `(id, user_id)`;
- unique-индекс хэша refresh-токена.

### `operator_connection_codes`

- `created_at timestamptz NOT NULL DEFAULT now()`;
- `used_at timestamptz NULL`;
- unique-индекс `code`;
- индекс `(operator_id, is_used, expires_at)`.

### `company_invitations`

- `created_at timestamptz NOT NULL DEFAULT now()`;
- `updated_at timestamptz NOT NULL DEFAULT now()`;
- `decided_at timestamptz NULL`;
- partial unique-индекс pending-приглашения `(company_id, operator_id) WHERE status='pending'`.

### Ограничения попыток

Для попыток кода допускается отдельная таблица с субъектом, началом окна, числом отказов и `locked_until`. Хранение только в памяти процесса запрещено.

### `audit_action_type`

Добавить значения `user_registered`, `profile_updated` и `company_created`. Для login/logout и приглашений использовать существующие `login`, `logout`, `invitation_sent`, `invitation_accepted`, `invitation_rejected`.

## 10. Архитектура Go

Рекомендуемая структура:

```text
internal/
  auth/
    service.go             бизнес-сценарии auth
    repository.go          интерфейсы хранения
    postgres.go            PostgreSQL-реализация
    password.go            Argon2id
    tokens.go              JWT и refresh
    middleware.go          проверка сессии и контекст пользователя
    errors.go              предметные ошибки
  companies/
    onboarding.go          атомарное создание первой компании
  staff/
    onboarding.go          коды и приглашения
  transport/
    web/auth.go            публичные camelCase DTO
    authinternal/session.go внутренний snake_case DTO
```

HTTP-обработчик отвечает только за разбор/валидацию DTO и перевод предметной ошибки в HTTP. Транзакции определяются на уровне сценария. Репозитории не возвращают GORM-модели наружу.

Зависимости `clock`, генератора случайных данных и token signer передаются явно, чтобы сроки, блокировки и токены тестировались детерминированно.

```text
AUTH_IDLE_TTL=24h
AUTH_LOGIN_WINDOW=10m
AUTH_LOGIN_MAX_FAILURES=5
AUTH_LOGIN_LOCK_DURATION=15m
AUTH_CODE_WINDOW=10m
AUTH_CODE_MAX_FAILURES=5
AUTH_CODE_LOCK_DURATION=15m
```

`SECRET` остаётся ключом подписи JWT. На production-подобном стенде значение короче 32 случайных байт должно отклоняться. Ошибки конфигурации не содержат значения секретов или DSN.

## 12. Изменения панели

В рамках интеграции API‑03 панель должна:

1. добавить `refreshToken` в `AuthResponse` и отдельное защищённое хранение refresh-токена;
2. изменить минимальную длину пароля с 6 на 8;
3. реализовать один общий refresh promise для параллельных `401`;
4. не запускать refresh для `/auth/login`, `/auth/register` и `/auth/refresh`;
5. после успешного refresh заменить access-токен и повторить отклонённый запрос один раз;
6. при ошибке refresh очистить оба токена и завершить сессию;
7. не повторять изменяющую операцию после сетевой ошибки без ответа;
8. читать серверную ошибку из `error.code` и `error.message`;
9. не завершать локальную сессию при `403 ACCESS_DENIED` внутренней аналитики во время онбординга.

Токены не выводятся в console, telemetry и error UI.

## 13. Audit и журналирование

Обязательные audit-события:

- регистрация пользователя;
- успешный login;
- logout и отзыв сессии;
- изменение собственного профиля;
- создание компании;
- создание, принятие и отклонение приглашения.

До компании `audit_logs.company_id` равен `NULL`. После прикрепления используется актуальная компания. Audit details не содержат пароль, токены, connection code, JWT, password hash или полный Authorization header.

Access-log содержит маршрут, метод, статус, длительность и request ID, но не тело auth-запроса и не заголовок Authorization.

## 14. Тестирование

### 14.1. Unit-тесты

Покрытие критической auth-логики — не менее 95%. Обязательные случаи:

- Argon2id hash/verify и неверный пароль;
- claims, подпись, неверный алгоритм, issuer/audience и сроки JWT;
- refresh hashing и отсутствие открытого токена в БД;
- пять неудачных входов, границы 10 и 15 минут, сброс после успеха;
- 24 часа бездействия и абсолютные 7 суток;
- матрица ролей до и после онбординга;
- валидация DTO и безопасное отображение ошибок;
- сроки кода относительно `00:00 Europe/Moscow`, включая смену календарного дня;
- повторное создание приглашения;
- запрет принимать чужое приглашение.

### 14.2. Интеграционные тесты с PostgreSQL

- миграция пустой БД и обновление БД после API-02;
- конфликт логинов без учёта регистра отклоняет миграцию;
- конкурентная регистрация одного логина создаёт одного пользователя;
- register создаёт пользователя, сессию и audit атомарно;
- rollback не оставляет частичных данных;
- конкурентное создание компании связывает администратора только с одной компанией;
- два одновременных accept из разных компаний дают ровно один успех;
- RLS не выдаёт пользователя/приглашение другой компании;
- logout немедленно отзывает access и refresh;
- блокировка пользователя делает существующую сессию недействительной;
- connection-code rate limit общий для двух экземпляров repository/service.

### 14.3. HTTP-тесты

- каждый метод проверяет успешный ответ и все контрактные ошибки;
- защищённая операция не выполняется до auth-проверки;
- ошибки соответствуют общему envelope и содержат request ID;
- публичный proxy не пропускает `/internal/auth/v1/session`;
- внутренний endpoint возвращает 200/400/401/403/503 по контракту;
- JSON с неизвестными полями и второй JSON-объект в теле отклоняются.

Тесты используют реальные PostgreSQL-зависимости для транзакций, блокировок, уникальных индексов и RLS. Ослаблять проверки ради прохождения тестов запрещено.

## 15. Критерии приёмки

Фича считается принятой, если выполняется весь следующий сценарий:

1. администратор регистрируется без компании и получает два токена;
2. `GET /auth/me` возвращает `companyId=null`, а analytics session — `403`;
3. администратор создаёт компанию и стартовые настройки одной транзакцией;
4. тот же access JWT открывает актуальный профиль с компанией;
5. оператор регистрируется как `unassigned_operator` и получает код до полуночи МСК;
6. администратор создаёт приглашение по коду;
7. оператор видит приглашение и принимает его;
8. оператор получает L1/L2 и компанию, остальные приглашения становятся недействительными;
9. login блокируется после пяти неверных попыток без раскрытия причины;
10. refresh выдаёт новый access JWT, включая случай с истёкшим access;
11. logout немедленно делает оба токена текущей сессии недействительными;
12. внутренний `/session` возвращает актуальные роль, компанию и срок;
13. токены, пароли, коды и хэши отсутствуют в логах;
14. unit, integration, race, coverage и статический анализ проходят.
